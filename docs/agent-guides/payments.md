# 支付、回调与额度安全

改充值/回调/补单/兑换码/订阅/额度缓存前必读。保留资金与验签不变量，不维护商户个人信息、订单号、已开支付方式数量或某天汇率余额。

## 通道启用与公网回调

- 支付合规确认、对应支付方式开关、所需配置完整、PayMethods声明缺一不可；设置未同步前不能误判通道故障。
- 配置以当前option与同步周期核对，不能以历史“已经开通”说明今天必可支付。设置改动需授权，不在诊断里输出私钥/商户密钥。
- 异步通知才是到账触发点；浏览器同步return不证明入账。退款/拒付的额度回收是独立业务功能，当前只处理成功通知不能承诺已覆盖它。
- 收银台用真实浏览器验证，服务端裸GET可能被支付宝FISHING_RISK拦，不等于商户配置错。真实付款测试先获授权，不拿归档中的小额例子当授权。

## 支付宝RSA2的两个方向

- 应用私钥签本站请求，支付宝公钥验支付宝响应/通知；二者本来不是同一密钥对，不能按“不配对”误判。
- **通知验签使用原始表单字段**，不把解析后结构体重序列化当签名源；omitempty可能删掉 `voucher_detail_list=[]` 这样的真实字段。
- 通知口径rsaCheckV1：排sign和sign_type、跳过空值、key排序、k=v拼接、RSA2；请求签名则保留sign_type。两个方向不能共用错误过滤表。
- app_id必须存在且严格等于当前应用；缺失/串应用/金额不符均拒绝并保留明确日志，不“非空时才校验”。
- 不能用本应用私钥自签一个假通知证明生产支付宝验签可用；那不是支付宝签名。离线单测可用受控密钥/固定真实协议fixture，但不能替代生产配置链证据。
- 只读 `alipay.trade.query` 查询不存在的订单可核对交易权限/响应签名而不建付款单；这也仍须遵守当前任务的授权边界，不自动执行。

## 入账必须原子、幂等

1. GORM v2行锁使用 `clause.Locking{Strength:"UPDATE"}`；旧 `gorm:query_option` 不生效。SQLite不支持同样的行锁，需依赖相应事务/CAS，不假装方言行为一致。
2. 状态流转用 `WHERE status=pending` 等条件更新，只有 RowsAffected==1 的那个事务加额度；合法签名可被重放，不靠验签防重复入账。
3. “订单置成功”与“增加额度”在**同一事务**，失败整体回滚，不能出现订单success却未充值且无法补单。
4. 真正加额度后同步Redis额度缓存；裸SQL只改数据库会使显示/后续计算读旧余额。
5. 已成功订单幂等回success；失败/过期等异常终态收到成功通知要明确人工介入，不能静默改成功或吞掉资金异常。
6. 管理员补单幂等分支没有真加额度时不写假成功日志；同样适用于兑换码、订阅和邀请额度转移的并发安全。

## 金额与成功响应

- 金额十进制只算一次，统一Round(2)到分；下发字符串、存库值、回调比较复用同一结果，不能float格式化和decimal各算一次。
- 二进制/十进制混合舍入在第三位为5时曾差0.01，导致已付款不入账；回归至少覆盖该边界与分组折扣，不靠随机大循环宣称安全。
- 所有网关回调**先提交入账，再回success**；异常/入账失败回fail让网关重试，不提前确认丢失重试机会。
- 只读同步return与异步notify分开，日志/订单状态/真实额度三方核对，不以跳转页面当付款证明。

## 回调限流与代理信任

- 回调用独立 PaymentNotifyRateLimit，不能直接套用户敏感操作的低阈值，避免高峰429掉合法付款。
- 阈值、时长、开关读当前配置，不固定记录某次生产流量。
- 来源IP只信实际nginx/可信代理，不能默认信任任意XFF；网络变化同步TRUSTED_PROXIES，不配全网段或全信任。
- 支付改动需同时验证正常到账、签名/金额/app_id拒绝、合法重放、并发幂等、异常终态与缓存一致性。测试mock或隔离库；生产付款/改余额不是默认验证步骤。

## 商品/套餐类订单（非充值）

充值订单与套餐/商品订单通常是两张表、两套回调，但**验签、金额比对、CAS 幂等口径必须一致**，不能因为“不是充值”就放松。

- 验签只能证明报文来自网关，**不能证明金额正确**：签名通过后仍要把回调金额与订单金额按同一份“舍入到分”的值比对，不符即拒绝。只验签不比对金额，等于允许用极小金额购买高价套餐。
- 支付方式**名字相同不代表收款通道相同**：聚合网关的通道名（如 alipay）与官方直连同名时，下单路由必须按“官方直连已开通且命中该方式”显式判定，并让前端按返回的 `pay_mode` 区分「表单 POST」与「整页跳转」两种拉起方式；两种都走表单会把收银台页面 POST 坏。
- 拉起支付失败必须把订单置为失败态，否则它永远停在 pending，页面永远等不到发货。
- 前端轮询只在存在 pending 订单时进行；长时间未确认要**降频但不停止**（异步通知可能迟到，停了轮询等于放弃这一单）；提示「支付成功」只针对本次会话中新变为成功的订单，历史成功订单不能每次刷新都弹一次。
- 商品交付（密钥/权益）由订单状态派生：未支付或已过期一律不下发，判定口径要与支付回调写回的状态一致。
